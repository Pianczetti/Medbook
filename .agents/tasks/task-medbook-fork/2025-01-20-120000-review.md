# PrestaShop 9 fork transformed into MedBook medical booking platform

A complete vertical pivot of PrestaShop 9 into a Polish medical appointment booking system. The `medbook_booking` module provides the entire domain: resource/schedule/booking engine, medical entities (doctor profiles, clinics, specializations, prescriptions, documents, consents), a multi-step booking flow, cart integration via virtual product + SpecificPrice, reminder/waitlist CLI commands, and a dedicated front-office theme. The installer is patched to default to Polish locale and auto-install the module on fresh setups.

Watch for: the front-office controllers reference database tables and columns that do not exist in any install or upgrade SQL (confirmed), the CSRF protection on the cart-booking AJAX endpoint has a bypass path for guests (confirmed), PESEL is stored in plaintext without encryption despite RODO scope (confirmed), and the `createBooking` transaction provides no real isolation guarantee against double-booking under concurrent load (likely).

## High-level view

The module's core booking engine (BookingFrontProvider, SlotCalculator, CartIntegrationService) is well-structured: slot calculation is a pure-logic service, pricing rules are layered with priority, and the cart flow integrates with PrestaShop's checkout via SpecificPrice records tied to a hidden virtual product. The architectural separation is clean.

The front-office theme and booking flow controllers use a completely different schema from the one installed by the module. Controllers like `bookingflow.php`, `dashboard.php`, `doctorprofile.php`, and `doctorsearch.php` query tables (`medbook_doctor`, `medbook_doctor_specialization`, `medbook_specialization_lang`, `medbook_doctor_favorite`, `medbook_doctor_meta`) with columns (`id_medbook_doctor`, `title`, `firstname`, `lastname`, `active`, `photo_url`, `rating`, `reviews_count`, `consultation_price`, `id_medbook_resource`) that are never created by the install.sql or any upgrade script. The actual schema creates `medbook_doctor_profile` with entirely different columns. These controllers will fail with SQL errors on a fresh install.

Medical data handling introduces RODO/GDPR exposure. PESEL (Polish national ID) is stored unencrypted in the prescription table, documents are stored in a predictable path structure under `upload/medbook_documents/{customer_id}/`, and the consent controller's grant/revoke actions lack CSRF protection. The data-export endpoint correctly scopes to the authenticated customer, but the data-retention table is never populated or enforced by any service.

The cart-booking AJAX endpoint (`cartbooking.php`) has a CSRF validation gap: when both the posted token and the cart's `secure_key` are empty (newly-created guest carts), the validation is explicitly skipped. This allows unauthenticated requests to add booking items to newly-created carts without any token verification.

2. **CSRF bypass for guest cart-booking** — In `cartbooking.php`, when both `$token` and `$secureKey` are empty (newly-created guest cart), the CSRF check is skipped entirely. Remove the bypass and generate a proper CSRF token independent of cart state.

3. **PESEL stored in plaintext** — The `medbook_prescription` table stores PESEL (national ID number) without any encryption. For a system declaring RODO compliance, this is a data-protection gap. Encrypt or hash the PESEL column at rest.

4. **Booking race condition under concurrency** — `BookingFrontProvider::createBooking()` wraps slot validation in a DB transaction, but without `SELECT ... FOR UPDATE` or table locks, concurrent requests can both see the slot as available and both insert. Use a pessimistic lock or a unique constraint on `(id_resource, booking_date, time_start)` with conflict handling.

5. **Document download path traversal risk** — `DocumentService::download()` constructs a file path from `$customerId` and `filename` stored in DB. If the filename column were tampered with (e.g., `../../etc/passwd`), the path concatenation would traverse. Validate that the resolved path stays within the expected upload directory.

6. **`handleExport` exits without Smarty rendering** — The consent controller's export action calls `echo` + `exit`, bypassing PrestaShop's response lifecycle. Use a proper `Response` object or at minimum `ob_end_clean()` to avoid partial output from the framework.

7. **`install()` overwrites `PS_SHOP_NAME`** — Module installation unconditionally sets `PS_SHOP_NAME` to `'MedBook'`, which would rename any existing shop. This should be gated to only run on fresh installs or removed from module-level install.

8. **Data retention table unused** — `medbook_data_retention` is created but no service reads or enforces retention rules. The RODO "right to be forgotten" claim in documentation is not backed by any automated cleanup.

9. **No test coverage** — 263 files, zero test files. Slot calculation logic (SlotCalculator) and pricing logic are pure services ideal for unit tests. The booking creation flow and cart integration need integration tests to verify race-condition handling.

## Schema divergence between booking engine and front-office controllers

The install.sql establishes a schema where doctors are represented as `medbook_doctor_profile` rows linked to `medbook_resource` via `id_resource`, with specialization as a single `id_specialization` FK on the profile. The front-office controllers (`bookingflow.php`, `doctorsearch.php`, `doctorprofile.php`, `dashboard.php`) query an entirely different set of tables:

- `medbook_doctor` with columns `id_medbook_doctor`, `title`, `firstname`, `lastname`, `active`, `photo_url`, `rating`, `reviews_count`, `consultation_price`, `bio`, `experience`, `pwz_number`, `id_medbook_resource`
- `medbook_doctor_specialization` (many-to-many join)
- `medbook_specialization_lang` (localized specialization names)
- `medbook_doctor_favorite` (patient favorites)
- `medbook_doctor_meta` (key-value education/certifications)
- `medbook_doctor_clinic` with columns like `id_medbook_doctor`, `id_medbook_clinic`
- `medbook_clinic` with columns `street`, `postal_code`, `city`, `phone`

None of these tables are created by `install.sql`, `upgrade-1.1.0.sql`, or `upgrade-1.2.0.sql`. The actual installed `medbook_doctor_clinic` uses `id_resource` and `id_clinic` (not `id_medbook_doctor` and `id_medbook_clinic`), and the actual `medbook_clinic` uses `address` (not `street`). The `medbook_specialization` table has no `_lang` companion table—names are stored directly on the specialization row.

This means the booking engine (BookingFrontProvider, CartIntegrationService, SlotCalculator) works against the correct schema, but the entire doctor-facing front-office (search, profile, booking flow, dashboard) will produce SQL "table not found" or "column not found" errors on any request.

## CSRF and authentication gaps on cart-booking endpoint

```php
// cartbooking.php lines 30-40
if ($secureKey !== '' || $token !== '') {
    if (!$token || $token !== $secureKey) {
        // reject
    }
}
```

When a guest user hits the endpoint and no cart exists yet, the code creates a new cart (line 25), then both `$secureKey` (from the freshly-created cart) and `$token` (from POST) can be empty strings. The conditional explicitly allows this case through. An attacker can POST directly to this endpoint without any token and create cart entries with arbitrary resource/time selections. This is a low-severity concern in isolation (the booking still needs payment to finalize), but combined with the deposit system it could be used to hold slots.

## Medical data stored without encryption

The `medbook_prescription` table stores `pesel VARCHAR(11)` in plaintext. PESEL is a Polish national identification number equivalent to SSN—it contains birth date and is used for identity verification. The system's RODO compliance documentation claims data protection, but the schema stores this value unencrypted. The `ConsentService` correctly tracks consent grants and revocations, and the data export works properly, but the actual sensitive data lacks encryption at rest.

The document upload path (`upload/medbook_documents/{customer_id}/{random_hex}.ext`) uses customer ID as a directory name. While the download endpoint correctly checks ownership via DB lookup, the filesystem path is predictable if directory listing is enabled or if there's an LFI elsewhere. The `DocumentService::download()` also doesn't validate that the resolved path from `$this->uploadDir . '/' . $customerId . '/' . $document['filename']` stays within the upload directory boundary—a filename stored as `../../sensitive_file` would traverse.

## Booking double-book potential

`BookingFrontProvider::createBooking()` opens a transaction, calls `getAvailableSlots()` (which is a SELECT), checks the slot is available, then INSERTs. Under READ COMMITTED (MySQL default for InnoDB), two concurrent transactions can both see the slot as available and both insert successfully—the unique constraint is on `reference_code`, not on the `(id_resource, booking_date, time_start)` tuple. The `UniqueConstraintViolationException` catch returns "slot no longer available" but only fires for reference code collisions (extremely unlikely with `random_bytes(5)`), not for actual double-bookings.

Adding a composite unique index on `(id_resource, booking_date, time_start, time_end)` for non-cancelled bookings (or using `SELECT ... FOR UPDATE` on the resource row) would provide actual protection.

## Module install side-effects on existing shops

The `install()` method calls `Configuration::updateValue('PS_SHOP_NAME', 'MedBook')`, which unconditionally renames the shop. If this module were installed on an existing PrestaShop instance (not a fresh MedBook install), it would silently rename the store. This belongs in the fixture installer or should be gated behind a "fresh install" check.

## Online visit implementation

`OnlineVisitService::generateMeetingUrl()` produces a URL like `/meeting/{bookingId}/{random_token}` but there's no controller or route handling this path. The URL is stored in `video_call_url` and sent in confirmation emails, but the actual video call infrastructure (WebRTC, Jitsi integration, or redirect to external service) is absent. The token generation provides URL unpredictability but the endpoint doesn't exist.

## Uninstall leaves orphan tables

The `uninstall.sql` only drops core tables (resource, resource_lang, schedule, booking, blocked_date) but not the medical tables added in the same install.sql: `medbook_specialization`, `medbook_clinic`, `medbook_doctor_profile`, `medbook_doctor_clinic`, `medbook_document`, `medbook_consent`, `medbook_data_retention`, `medbook_prescription`, `medbook_cart_data`, `medbook_confirm_token`, `medbook_reminder`, `medbook_recurrence_config`, `medbook_suggested_visit`, `medbook_waitlist`, `medbook_price_rule`, `medbook_deposit_rule`, `medbook_addon`, `medbook_addon_lang`, `medbook_booking_addon`, `medbook_refund_rule`. A module uninstall leaves 18+ orphan tables.
