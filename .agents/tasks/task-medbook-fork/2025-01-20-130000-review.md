# MedBook medical booking platform — v2 verification (v2)

The seven fixes from v1 are all present and correctly implemented: front controllers now query the actual schema (`medbook_resource`, `medbook_doctor_profile`, `medbook_doctor_clinic`, `medbook_clinic`); `uninstall.sql` drops all 25 tables in dependency order; `cartbooking.php` requires a non-empty token matching `cart->secure_key` unconditionally; `DocumentService::download()` validates `realpath` stays within the upload directory; `PrescriptionService` encrypts PESEL with AES-256-CBC; `install.sql` adds a UNIQUE constraint on `(id_resource, booking_date, time_start, time_end)`; and `PS_SHOP_NAME` is only set when the current value is empty or `'PrestaShop'`. The consent export uses `ob_end_clean()` + `die()`.

Watch for: the UNIQUE booking constraint blocks rebooking of cancelled slots (confirmed), `DocumentService::delete()` lacks the same path-traversal guard applied to `download()` (confirmed), and consent grant/revoke actions remain unprotected by CSRF tokens (confirmed).

## High-level view

The double-booking UNIQUE constraint (`uniq_medbook_booking_slot`) is unconditional — it covers all rows regardless of status. When a booking is cancelled, the row remains with the same `(id_resource, booking_date, time_start, time_end)` tuple, so any attempt to rebook that slot will violate the constraint. The slot-availability query filters out cancelled bookings, meaning the UI shows the slot as free while the INSERT will fail.

`DocumentService::delete()` performs the same filename-to-path construction as `download()` but skips the traversal check entirely, calling `unlink()` on the unvalidated path. A tampered `filename` column in the database would allow arbitrary file deletion.

The consent controller's `handleGrant()` and `handleRevoke()` methods execute state-changing operations via GET parameters with no CSRF token validation. Any page that can trigger a request to `?action=grant&consent_type=marketing` will silently grant consent for the authenticated user.

The v1 issues #8 (data retention unused) and #9 (no test coverage) remain unaddressed as expected.

## Cancelled bookings poison the UNIQUE slot constraint

The fix for v1 issue #4 added `UNIQUE KEY uniq_medbook_booking_slot (id_resource, booking_date, time_start, time_end)` to `medbook_booking`. `cancelBooking()` in `BookingFrontProvider` sets `status = 'cancelled'` but leaves the row in place. `getExistingBookings()` excludes cancelled rows:

```sql
WHERE status NOT IN ('cancelled')
```

So the UI shows the cancelled slot as available. When the customer rebooks, `createBooking()` inserts a new row with the same tuple. MySQL rejects it because the cancelled row occupies that unique slot. The `UniqueConstraintViolationException` catch returns "Selected time slot is no longer available" — confusing for a slot the system just showed as free.

The same problem applies to `CartIntegrationService::finalizeBooking()`, which also inserts into `medbook_booking` and would hit the same constraint for a previously-cancelled slot.

Options: physically DELETE on cancel; use a generated column `status_active` (1 if non-cancelled, NULL otherwise) and make the UNIQUE include it (MySQL allows multiple NULLs in unique keys); or use a separate `slot_lock` table with only active reservations.

## DocumentService::delete() bypasses traversal guard

`download()` (lines 83-99) applies:

```php
$realPath = realpath($filePath);
$allowedBase = realpath($this->uploadDir);
if ($realPath === false || $allowedBase === false || !str_starts_with($realPath, $allowedBase . DIRECTORY_SEPARATOR)) {
    return null;
}
```

`delete()` (lines 152-170) constructs the path identically but calls `unlink($filePath)` on the raw concatenation. A filename like `../../config/settings.inc.php` would result in `unlink('/path/to/upload/medbook_documents/123/../../config/settings.inc.php')` succeeding. Extract the `realpath` check into a private helper and call it from both methods.

## Consent state changes without CSRF

The consent controller dispatches on `Tools::getValue('action', '')`:

```php
if ($action === 'grant') {
    $this->handleGrant($consentService, $customerId);
} elseif ($action === 'revoke') {
    $this->handleRevoke($consentService, $customerId);
}
```

Both methods directly execute database writes with no `Tools::isSubmit()` check, no token comparison, no POST requirement. A link like `<img src="...consent?action=grant&consent_type=marketing">` on any page the patient visits would silently grant marketing consent. CSRF attacks target exactly authenticated sessions.

## PESEL encryption key stored alongside application code

The `PrescriptionService` falls back to `_COOKIE_KEY_` (defined in `config/settings.inc.php`) when no explicit `$encryptionKey` is injected. This means PESEL encryption at rest only protects against DB-only breaches — filesystem access exposes both the key and the data. For a medical platform handling national IDs, a dedicated secret (injected via environment variable or a key management service) would provide defense in depth.
